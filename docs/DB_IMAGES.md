# Database images and `falak-db`

Every managed database runs in a container built from a Falak image (plan: `docs/plans/V0_10_PRODUCTION.md` §3, §5).
Each image is the official image, pinned by digest, plus `falak-db`: a small static Go binary (`agent/cmd/falak-db`,
logic in `agent/internal/dbhelper`). It is the container's entrypoint and healthcheck, and the one thing the agent
runs with `docker exec` for backups, restores, and WAL or binlog spooling. The agent never builds shell strings.

## Images

`ghcr.io/falak-sh/falak-<engine>`, built by `.github/workflows/db-images.yml` from `images/db/<engine>/Dockerfile`
and `images/db/versions.json`.

| Engine | Tags | Base (pinned by digest) | Added | Arch |
|---|---|---|---|---|
| PostgreSQL | `15`, `16`, `17`, `18` | `postgres:<v>-bookworm` | `falak-db` | amd64, arm64 |
| MySQL | `8.0`, `8.4` | `mysql:<v>` (Oracle Linux 9) | Percona XtraBackup 8.0.35-36 / 8.4.0-7, `mysqlbinlog`, `falak-db` | amd64, arm64 |
| MariaDB | `10.11`, `11.4` | `mariadb:<v>` (Ubuntu) | `falak-db` (mariadb-backup is in the base) | amd64, arm64 |
| Redis | `7.4`, `8` | `redis:<v>` | `falak-db` | amd64, arm64 |
| Valkey | `8.1` | `valkey/valkey:<v>` | `falak-db` | amd64, arm64 |

Percona publishes XtraBackup for Oracle Linux 9 on both x86_64 and aarch64, so every tag is multi-arch.

The MySQL image also drops MySQL Shell (unused, and it bundles its own Python packages), and takes `mysqlbinlog`
from the `mysql-community-client` RPM of the exact server version, checked against MySQL's signing key. Every image
applies the distribution's pending security updates on top of the pinned base.

**Tags**

| Built from | Tags |
|---|---|
| `main`, and the weekly rebuild (Mondays) | `<version>`, `<version>-falak<run>` |
| `release/**` branches | `<version>-rc`, `<version>-rc-falak<run>` |
| tags `vX.Y.Z` | `<version>-vX.Y.Z` |
| pull requests | nothing: build, test and scan only |

`<run>` is the workflow's run number, so a weekly rebuild produces a new `-falak<run>` tag, which is offered as a
minor upgrade. Instances record the image **digest**; tags are only for discovery.

**What is published is what was tested.** Each architecture is built once, on a native runner, into an OCI archive;
that archive's image is smoke-tested and scanned, then pushed by digest (skopeo, digests preserved). The multi-arch
index is created from those digests, and the build jobs hold a read-only token without persisted credentials; only
the publish job can write packages or get an OIDC token.

The index and its platform images are signed with cosign keyless (GitHub OIDC), and each platform image carries an
SPDX SBOM attestation (generated by Trivy from the published archive). To check an image:

```sh
id='^https://github.com/falak-sh/falak/\.github/workflows/db-images\.yml@refs/(heads/main|heads/release/.+|tags/v.+)$'
cosign verify ghcr.io/falak-sh/falak-postgres:17 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com --certificate-identity-regexp "$id"
# The SBOM is attached to each platform image:
digest=$(docker buildx imagetools inspect ghcr.io/falak-sh/falak-postgres:17 --format '{{json .Manifest}}' |
  jq -r '.manifests[] | select(.platform.architecture == "amd64") | .digest')
cosign verify-attestation --type spdxjson "ghcr.io/falak-sh/falak-postgres@$digest" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com --certificate-identity-regexp "$id"
```

### Trust: the control plane ships the digests

Servers run a database image only by the digest the control plane sends (`db.instance.create|update` refuse an
`instance.digest`-less spec; the agent checks the pulled image's RepoDigests against it). The control plane only sends
digests from `control-plane/modules/Databases/config/db-image-digests.json` (`{"postgresql": {"17": "sha256:…"}}`), and
refuses to create or upgrade to a major missing there. That file is written in CI:

- `release.yml` (tags `vX.Y.Z`, `vX.Y.Z-rc.N`): its `db-digests` job runs `tools/db-image-digests.sh -<tag>`, which
  resolves the multi-arch index digest of `ghcr.io/falak-sh/falak-<engine>:<version>-<tag>` for every entry of
  `images/db/versions.json`. The db-images run of the same tag pushes those tags only after building, testing, scanning
  and signing them, so the job waits for them (up to 2 h, `--wait`); any image still missing fails the release. The
  control-plane image is then built with the file.
- The committed file is `{}`: a control plane built from a checkout (development, the sim) creates no database until
  you run the script, with `-rc` (release/** branches), `""` (main: `<version>`) or `-vX.Y.Z`, after `docker login
  ghcr.io` if the packages are private.

So the chain is: db-images (GitHub OIDC) builds and signs → the release job pins exactly those digests into the
control-plane image, which is itself built by CI from the same tag → the agent runs nothing else. A digest is
content-addressed: a registry or mirror cannot substitute other bytes for it. Verifying cosign signatures on every
server would add a Sigstore client, network access to Rekor/Fulcio and a trust root to keep current on each server,
to check a fact CI already established when it chose the digest. The signatures stay useful to anyone auditing an
image (above) or a control plane built outside CI.

## Running an image

The container starts as root, like the base image; the official entrypoint drops to the engine's user (`postgres`,
`mysql`, `redis`, `valkey`) after preparing the data directory. `stop_grace_period` should be 60 s.

| | PostgreSQL | MySQL / MariaDB | Redis / Valkey |
|---|---|---|---|
| Data volume | `/var/lib/postgresql/data` (15–17), `/var/lib/postgresql` (18: `PGDATA=/var/lib/postgresql/18/docker`) | `/var/lib/mysql` | `/data` |
| Password file | `POSTGRES_PASSWORD_FILE` | `MYSQL_ROOT_PASSWORD_FILE` / `MARIADB_ROOT_PASSWORD_FILE` | `FALAK_DB_PASSWORD_FILE` |
| Port | 5432 | 3306 | 6379 (TLS-only when TLS is on) |

**Passwords only come from files.** `falak-db init` refuses to start when `POSTGRES_PASSWORD`, `MYSQL_ROOT_PASSWORD`,
`MYSQL_PASSWORD`, `MARIADB_ROOT_PASSWORD`, `MARIADB_PASSWORD`, `*_ALLOW_EMPTY_*`, `*_RANDOM_ROOT_PASSWORD`,
`POSTGRES_HOST_AUTH_METHOD`, `MARIADB_ROOT_PASSWORD_HASH`, `MARIADB_PASSWORD_HASH`, `REDIS_PASSWORD` or
`VALKEY_PASSWORD` is set. The file must be readable by the engine's user (the postgres entrypoint reads it after
dropping privileges), and the password must not contain a line break or NUL. `FALAK_DB_PASSWORD_FILE` works for
every engine: when the engine's own variable is not set, init hands it to the official entrypoint under that name,
so first-time initialisation uses it too.

MySQL-family tools get the credentials as an option file on file descriptor 3 (a pipe: nothing on disk, in argv or
in the environment). xtrabackup and mariadb-backup read their option files twice, which a pipe can't serve, so they
get a 0600 file in a private directory on the container's tmpfs (`/dev/shm`), removed when they exit.

| Variable | Default | |
|---|---|---|
| `FALAK_DB_ENGINE` | set by the image | |
| `FALAK_DB_SETTINGS` | `{}` | settings JSON, below; not secret |
| `FALAK_DB_SETTINGS_FILE` | unset | a file holding the settings JSON, read at every start instead of `FALAK_DB_SETTINGS` (the agent rewrites it, so a change is a restart, not a new container) |
| `FALAK_DB_PREVIOUS_PASSWORD_FILE` | unset | redis/valkey: a previous password that stays valid next to the current one (a rotation's overlap) |
| `FALAK_DB_MEMORY_BYTES` | the cgroup limit (v2, then v1), else the host's RAM | what the config is tuned to |
| `FALAK_DB_TLS_DIR` | `/run/falak/db/tls` | `server.crt`, `server.key`, optional `ca.crt` (read-only mount) |
| `FALAK_DB_SPOOL` | `/var/lib/falak/db/spool` | mount the instance volume's spool directory here |
| `FALAK_DB_QUERY_INSIGHTS` | unset | `1`: load what top queries need at start (PostgreSQL `pg_stat_statements`, MariaDB `performance_schema`). The agent writes `query-insights.json` (`{"enabled": true}`) next to `FALAK_DB_SETTINGS_FILE` instead, which wins. Not a setting: images before v0.16.0 reject unknown settings |

```sh
docker run -d --name falak-db-x --memory 1g --stop-timeout 60 \
  -v x-data:/var/lib/postgresql/data -v x-spool:/var/lib/falak/db/spool \
  -v /etc/falak/db/x/secrets:/run/secrets:ro -v /etc/falak/db/x/tls:/run/falak/db/tls:ro \
  -e POSTGRES_PASSWORD_FILE=/run/secrets/password -e FALAK_DB_SETTINGS='{"max_connections": 200}' \
  ghcr.io/falak-sh/falak-postgres:17
```

### Settings

Unknown fields are rejected. Zero values take the defaults.

| Field | Engines | Default | |
|---|---|---|---|
| `max_connections` | postgres, mysql, mariadb | 100 / 151 | |
| `server_id` | mysql, mariadb | 1 | unique per instance (binlogs) |
| `binlog_retention_hours` | mysql, mariadb | 168 | binlogs kept on the volume (they are spooled anyway) |
| `tls` | all | `true` | serve TLS with the mounted certificate |
| `require_tls` | all | `false` | postgres `hostssl` only, MySQL/MariaDB `require_secure_transport` (Redis is TLS-only whenever `tls` is on) |
| `slow_query_ms` | all | 1000 (redis/valkey 10) | 0 = off |
| `eviction` | redis, valkey | `noeviction` | `maxmemory-policy` |
| `persistence` | redis, valkey | `rdb` | `rdb`, `aof` or `none` |
| `bind` | redis, valkey | `["*", "-::*"]` | |
| `read_only` | postgres, mysql, mariadb | `false` | refuse writes from the config, so it holds across restarts (a point-in-time restore's copy): postgres `default_transaction_read_only`, MySQL `super_read_only` + `read_only`, MariaDB `read_only` (not root). falak-db's own sessions are not held back |
| `event_scheduler` | mysql, mariadb | `true` | `false`: no scheduled events (binlog replay, inspection) |

### Rendered config (at every start)

| Engine | File | Tuned to the memory limit | Always |
|---|---|---|---|
| PostgreSQL | `/etc/falak/db/postgresql.conf`, `pg_hba.conf` (passed as `-c config_file=`) | `shared_buffers` 25%, `effective_cache_size` 75%, `work_mem` (memory − shared buffers) / (4 × connections) in 4–256 MB, `maintenance_work_mem` 1/16 in 16 MB–2 GB | `wal_level=replica`, `archive_mode=on`, `archive_command='falak-db wal-push %p'`, `archive_timeout=60`, SCRAM, TLS, `log_min_duration_statement`, `include_if_exists` of the data directory's `falak-recovery.conf` |
| MySQL | `/etc/mysql/conf.d/zz-falak.cnf` | InnoDB buffer pool 55% (chunk size = pool below 1 GiB, so MySQL does not round it up to 128 MiB; whole chunks above), `performance_schema=OFF` below 1 GiB | `log_bin`, `binlog_format=ROW`, `binlog_row_image=FULL`, `sync_binlog=1`, `innodb_flush_log_at_trx_commit=1`, `gtid_mode=ON`, `enforce_gtid_consistency=ON`, slow log |
| MariaDB | same file | buffer pool 55% | the same, with `gtid_strict_mode=ON` (GTID is native) |
| Redis / Valkey | `/etc/falak/db/kv/server.conf` + ACL file | `maxmemory` 80% | persistence, TLS, a private Unix socket for falak-db (`/run/falak-db/server.sock`, 0700), an ACL file holding the password's SHA-256 (never the plaintext). The default user has `+@all -config -debug -module`. |

pg_hba: the Unix socket is `trust` (only processes in the container reach it; falak-db and the official entrypoint
use it); TCP is `scram-sha-256` (`hostssl` with `require_tls`).

The MySQL/MariaDB slow log is `/var/log/falak-db/slow.log` in the container (mysqld can't log to a pipe such as
`/dev/stderr`). Everything else logs to stderr.

## `falak-db` CLI

```
falak-db <command> [flags]      (--engine overrides FALAK_DB_ENGINE on every command)
```

SQL and passwords never travel in arguments: `psql` and `mysql` read their statements on stdin.

**Output.** A command prints one JSON object on stdout. Commands whose stdout is a data stream (`backup ...`) print
their JSON result as the last stderr line, prefixed with `falak-db-result: `. Errors go to stderr as
`falak-db: <message>`; secrets never appear in arguments, output or errors.

**Exit codes.** `0` done · `1` failed · `2` usage (bad flags or settings) · `3` not supported for this engine ·
`4` conflict (a spooled file with different content, a non-empty target directory, a running Redis on restore) ·
`5` not found (`wal-fetch`).

| Command | Server | Result |
|---|---|---|
| `init [-- server args]` | starts it | the image's entrypoint: checks the environment, installs the TLS files (key 0600, owned by the engine's user), renders the config, creates the spool (`spool` itself root's, 0755; only `spool/<kind>` the engine's), then `exec`s `docker-entrypoint.sh` with the engine's server and config |
| `config render [--memory-bytes N] [--settings JSON]` | any | writes the config (applied on the next start); `{"engine","memory_bytes","files","tuning"}` |
| `health` | running | `pg_isready` / `mysqladmin ping` / `PING` over TCP or the private socket; `{"engine","status":"healthy"}`, exit 1 when not. TCP, so the socket-only server the official entrypoints run during first-time initialisation does not count as ready. |
| `stats` | running | Open client connections and the server limit: postgres `pg_stat_activity` client backends vs `max_connections`, MySQL/MariaDB `SHOW GLOBAL STATUS` `Threads_connected` vs `@@max_connections` (works with performance_schema off), Redis/Valkey `INFO clients` `connected_clients` vs `maxclients` (Redis 7+; `CONFIG` is denied to the default user); `{"connections","max_connections"}`. The agent polls it at most once a minute per instance for the heartbeat (the control plane alerts above 80%). Images built before v0.10.0 answer exit 2 (unknown command): no connection figures. |
| `observe [--detail] [--cursor JSON]` | running | Engine figures for the agent's once-a-minute pass (docs/plans/OBSERVABILITY.md phase 3): cumulative `counters`, `gauges`, `labels`, `settings`, the container's cgroup `memory`, `query_insights` (`on` / `off` / `unavailable` with a reason), new `slow` entries since `--cursor` (MySQL / MariaDB slow log file from an inode + offset, truncated past 64 MiB; Redis / Valkey `SLOWLOG GET`), and with `--detail` `statements` (`pg_stat_statements` / statement digests, 100 by total time), `databases`, `tables`, unused `indexes`. Query text is normalized (no literals); Redis commands keep their name and key count. Best effort per section (`warnings`). Images built before v0.16.0 answer exit 2. |
| `reload` | running, SQL engines | renders the config again and applies the slow query threshold in place (PostgreSQL `pg_reload_conf()`, MySQL / MariaDB `SET GLOBAL slow_query_log` / `long_query_time`, new sessions); `{"reloaded","applied","slow_query_ms"}`. Redis / Valkey: exit 3 (`CONFIG` is denied to the default user) |
| `backup logical --database DB --out -` | running | postgres `pg_dump -Fc`; mysql `mysqldump --single-transaction --routines --triggers --events --hex-blob --set-gtid-purged=OFF`; mariadb `mariadb-dump` (same flags); redis/valkey `BGSAVE` (waits for a new `rdb_saves`), then the RDB (no `--database`). Result: `{"kind":"logical","format","database","bytes","sha256","started_at","finished_at"}` |
| `restore logical --database DB --in - [--clean \| --swap] [--owner ROLE]` | running (redis/valkey: **stopped**) | `pg_restore --no-owner --no-acl --exit-on-error` (`--clean --if-exists` with `--clean`) into an existing database; `mysql --binary-mode --system-command=OFF DB` (MySQL clients older than 8.0.40 / 8.4.3 are refused), `mariadb --binary-mode --sandbox DB`, so client commands in a dump (`\!`, `system`, `source`) can't reach the container; postgres `--swap`: into a scratch database (`<db>__falak_restore`), renamed into place only when complete (the old one moved aside, then dropped); `--owner`: every object handed to ROLE (`reassign`); redis/valkey: replaces `dump.rdb` and moves an AOF directory aside (`appendonlydir.before-restore-<time>`) |
| `backup physical --out -` | running | postgres: `pg_basebackup -D - -Ft -X none --checkpoint=fast` (one tar, no WAL); result adds `start_wal`, `stop_wal`, `label`. mysql: `xtrabackup --backup --stream=xbstream`; mariadb: `mariadb-backup --backup --stream=xbstream` |
| `restore physical --in -` | **stopped**, empty data dir | postgres: unpacks the tar (files and directories only; links, devices, absolute paths and `..` are refused); mysql/mariadb: `xbstream`/`mbstream -x`, then `--prepare`. Then chowns to the engine's user. `{"data_dir","files","bytes","start_wal"|"prepared"}` |
| `recover --wal-dir DIR [--target-time T [--action promote\|pause\|shutdown]]` | postgres, **stopped**, after `restore physical` | writes `recovery.signal` and `falak-recovery.conf` (`restore_command = 'falak-db wal-fetch %f %p --from DIR'`, `recovery_target_time`, `recovery_target_action`); recovery happens on the next start. `DIR` must be `/replay`, the spool, or under one of them; only the directory and the WAL files directly in it are handed to postgres. `--action` needs `--target-time`. Once postgres has promoted (no `recovery.signal` left), the next `init` removes `falak-recovery.conf`. `{"mode":"on-start",...}` |
| `recover --binlog-dir DIR [--target-time T]` | mysql/mariadb, **running**, after `restore physical` and a start | replays `mysqlbinlog --start-position=<backup position> --stop-datetime=T <binlogs from the backup's file on> \| mysql --binary-mode` (sandboxed as above; UTC); `DIR` is restricted like `--wal-dir`; refuses gaps in the binlog sequence. T is rounded **down** to the second: binlog timestamps have whole seconds, and replay stops before the first event at or after T. `{"mode":"replayed","binlogs","start_position"}` |
| `promote` | postgres, paused recovery | `pg_promote()`, then removes `falak-recovery.conf` |
| `wal-push PATH` | postgres (its `archive_command`) | spools the segment; silent on success |
| `wal-fetch NAME DEST --from DIR` | postgres (its `restore_command`) | copies `DIR/NAME` to `DEST`; exit 5 when absent (the end of the archive for postgres) |
| `binlog-rotate [--no-flush] [--restart]` | mysql/mariadb, running | `FLUSH BINARY LOGS`, then spools every closed binlog not spooled yet, oldest first. `{"flushed","current","spooled":[{"name","path","bytes","sha256","existed"}],"gaps":[{"kind","from","to","detail"}]}`. A break in the chain prints the result and **exits 4**: `missing` (binlogs purged before they were spooled; what remains is spooled, reported once) or `reset` (the numbering went backwards; nothing is spooled until `--restart`, after a new base backup). | `database create --name N [--charset C] [--collation X] [--owner O]` | running, SQL engines | creates the database when missing (postgres: `ENCODING 'UTF8' TEMPLATE template0`, converges the owner; mysql/mariadb: `utf8mb4` unless given). `{"changed"}` |
| `database drop --name N` | running, SQL engines | drops it when present (postgres `WITH (FORCE)`). `{"changed"}` |
| `user apply --spec FILE` | running, SQL engines | the user's full desired state from a JSON file the agent puts in the secrets directory (`{"username","password","host","grants":[{"database","privileges"}],"state":"present"\|"absent"}`): creates or alters the user and its password, grants the listed databases and revokes the others. The engine's own accounts are refused. `{"changed"}` |
| `password set --file FILE [--keep-current]` | running | the superuser's (postgres), root's (every `root@host`, mysql/mariadb) or the default user's (redis/valkey: `ACL SETUSER default resetpass #<sha256>`, and the ACL file rewritten) new password, read from FILE. falak-db connects with the current password file (mysql/mariadb: with the new one when the engine already has it, so a retry finishes); the agent replaces that file afterwards. redis/valkey `--keep-current`: the new password is added, the current one stays valid. `{"changed": true}` |
| `readonly on\|off` | running, SQL engines | postgres: `default_transaction_read_only` on every database, and the open client sessions are ended; mysql: `super_read_only`; mariadb: `read_only`. `{"read_only"}` |
| `table-counts --database DB` | running | the exact row count of every table: `{"database","tables":{"schema.table":n}}` (a copy is checked against its source; restore drills compare with the counts taken at backup time). Redis / Valkey: the keys of every logical database, `{"tables":{"db0":n}}` (no `--database`) |
| `query --database DB` | running, SQL engines | a restore drill's check query, on stdin: one `SELECT` (or `WITH … SELECT`), no `;`, comments or `\`, line breaks become spaces; run as `SELECT count(*) FROM (<query>)` in a read-only transaction as a temporary role dropped afterwards: postgres a login role with `pg_read_all_data`, `statement_timeout = 60s` and read-only transactions set on it; mysql/mariadb a user with `SELECT` on the database, a 60 s statement limit and the sandboxed client flags of `restore logical`. `{"database","rows"}` |
| `reassign --database DB --owner ROLE` | running, postgres | the database, its schemas and every object in them (tables, views, sequences, functions, types; not extensions') owned by ROLE |
| `version` | any | `{"version","engine"}` |

`T` is RFC 3339 (`2026-10-07T12:00:00Z`). Postgres keeps fractional seconds; MySQL/MariaDB round T down to the
second.

### The spool

`$FALAK_DB_SPOOL/wal/` (postgres) and `$FALAK_DB_SPOOL/binlog/` (mysql/mariadb) on the instance's volume. falak-db
**only adds files**: each one is written to a temporary file, fsynced, hard-linked into place (never replacing a file)
and the directory is fsynced. Spooling the same file twice is fine; different content under an existing name is exit
4 and the spooled file stays as it was. falak-db never deletes from the spool: shipping it (presigned URLs from the
CP, encrypted like backups: docs/BACKUPS.md) and removing what was shipped is the host agent's job. Names starting with `.` are
falak-db's own (temporary files, `.binlog-last`, the last binlog spooled, so shipped binlogs are not spooled again)
and must not be shipped or deleted.

Postgres pushes a segment at least every 60 s (`archive_timeout`). Binlogs are closed by `binlog-rotate`, which the
agent runs every 60 s.

## Physical backups and point-in-time recovery

**PostgreSQL: `pg_basebackup` + postgres' own archiving, no wal-g.** The plan named wal-g; the spool design makes it
unnecessary. WAL already leaves through `archive_command` into the spool, the agent ships and encrypts it, and
`restore_command` reads it back, so wal-g would only add a second copy path, its own storage layout and a large
binary to keep patched. A base backup is `pg_basebackup -Ft -X none` streamed to stdout. With archiving on, the
server ends a base backup only once every WAL segment it needs is archived, so when the command returns,
`start_wal`..`stop_wal` (from `backup_label` and the backup manifest in the stream) are in the spool.

Restore to a time T, in a **new instance** (the running one is never touched):

1. Create the new volume. With the server stopped (`docker run --rm --entrypoint falak-db ... restore physical --in -`),
   unpack the newest base taken before T.
2. Put the WAL from `start_wal` up to T (the agent fetches and decrypts it) into a directory mounted under `/replay`, and run
   `falak-db recover --wal-dir DIR --target-time T`.
3. Start the instance. It replays to T, then (default `--action promote`) opens on a new timeline. The original is
   untouched, so promoting is safe, and read-only inspection is enforced by the agent (for example
   `ALTER SYSTEM SET default_transaction_read_only = on`). `--action pause` keeps it in recovery for read-only
   queries, but a paused standby still holds the locks of transactions in flight at T: the table a later
   `DROP TABLE` touched can't even be read until `falak-db promote`. If T is past the last WAL available, postgres
   refuses to start ("recovery ended before configured recovery target was reached").

**MySQL / MariaDB: xtrabackup / mariadb-backup + binlogs.** A base backup is an xbstream on stdout; it records the
binlog file and position it is consistent with (`xtrabackup_binlog_info` / `mariadb_backup_binlog_info`).

1. With the server stopped, `restore physical --in -` into the new, empty volume (extract and `--prepare`).
2. Start the instance (the restored data keeps the source's users and root password).
3. Put the spooled binlogs (from the backup's file on) in a directory mounted under `/replay` and run
   `falak-db recover --binlog-dir DIR --target-time T`: `mysqlbinlog --stop-datetime` replays up to T (rounded down to the
   second) into the server.

## Building and testing locally

```sh
images/db/build.sh postgres 17                # -> falak-postgres:17-local (add --platform linux/amd64 to cross-build)
images/db/test.sh postgres 17                 # build, then the smoke tests against real containers
IMAGE=falak-postgres:17-local images/db/test.sh postgres 17   # test an existing image
IMAGE=falak-postgres:17-local images/db/drill-test.sh postgres 17   # a restore drill's hardening: cap-drop ALL + the
                                              # entrypoint's capabilities, no-new-privileges, pids, no network
SKIP_PITR=1 images/db/test.sh mysql 8.4       # skip physical backup + PITR
IMAGE=falak-mysql:8.4-local images/db/pitr-test.sh mysql 8.4   # the agent's whole PITR flow: shipping, a base, a restore
                                              # to a time into a new instance (docs/BACKUPS.md)
cd agent && go test ./internal/dbhelper       # unit tests (config golden files: go test ./internal/dbhelper -update)
```

`test.sh` starts the image with `*_FILE` secrets and a self-signed certificate, then checks the healthcheck, that the
password is not in the container's environment, the memory tuning, TLS, a database, a logical backup and restore,
WAL archiving (postgres) or binlog rotation and spooling (mysql/mariadb), and a physical backup restored into a new
volume and recovered to a time between an `INSERT` and a `DROP TABLE`. For Redis/Valkey: an RDB backup and an
offline restore.

## Bumping versions

- **Base images:** `images/db/bump.sh` re-resolves every tag in `versions.json` (and the Go builder image) to its
  current digest; `--check` only reports. Rebuild and run `test.sh` for the changed images, then commit
  `versions.json`. A new major (PostgreSQL 19) is a new entry in `versions.json` (and in the agent's allowed list).
- **XtraBackup:** pick the newest RPM for the series in Percona's repository
  (`https://repo.percona.com/pxb-80/yum/release/9/RPMS/<arch>/`, `pxb-84-lts` for 8.4), set `XB_VERSION`, and
  set `XB_SHA256_AMD64` / `XB_SHA256_ARM64` to `sha256sum` of the x86_64 and aarch64 RPMs. XtraBackup must support the
  server version in the base image: the PITR step of `test.sh` fails if it does not.
- **Trivy:** a fixable HIGH or CRITICAL finding fails CI. Fix it by bumping the base, or, when the code is not
  reachable, add the CVE to `images/db/.trivyignore` with a reason. `images/db/trivy.yaml` skips `gosu` (built by
  the upstream images with an old Go toolchain; it only drops privileges at start).
